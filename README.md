# CRM отдела продаж недвижимости

Единое веб-приложение для управления каталогом недвижимости, клиентами, бронированиями, сделками и отчётами. Интерфейс — HTML/CSS/JavaScript, API — FastAPI, хранение — SQLite через SQLAlchemy 2. Приложение сохраняет маршруты `/user/signin`, `/catalog/` и `/catalog/{property_id}` и расширяет их модулями клиентов, бронирований, сделок и аналитики. Код организован в `database/`, `models/`, `routes/`, `web/`.

## Запуск в Windows (Git Bash)

Распакуйте архив, например, в `C:\tmp`. Перейдите в каталог `realty_crm`, создайте виртуальное окружение, установите зависимости и запустите сервер:

```bash
cd /c/tmp/realty_crm
python -m venv venv
source venv/Scripts/activate
python -m pip install -r requirements.txt
python -m uvicorn main:app --host 127.0.0.1 --port 8000
```

Откройте в браузере http://127.0.0.1:8000/. Документация API доступна по адресу http://127.0.0.1:8000/docs. Остановка — Ctrl+C. Для повторного запуска достаточно активировать venv и выполнить последнюю команду. Не открывайте `web/index.html` двойным щелчком: интерфейс и API обслуживаются одним сервером.

При первом запуске автоматически создаётся `data/crm.db` с восемью исходными карточками объектов, клиентами, бронированиями, сделками и учётными записями. Дальнейшие запуски не перезаписывают данные. Удаление файла БД уничтожит записи; сохраняйте его резервную копию при остановленном сервере. Не используйте базу данных от прежних версий, схемы различаются.

## Первоначальные учётные записи

| Роль | Логин | Начальный пароль |
| --- | --- | --- |
| Руководитель | director | Director2026! |
| Менеджер | manager | Manager2026! |
| Клиент | client | Client2026! |

Поменяйте начальные пароли в разделе «Профиль и настройки». До первого запуска можно задать собственные пароли переменными окружения `CRM_PASSWORD_DIRECTOR`, `CRM_PASSWORD_MANAGER`, `CRM_PASSWORD_CLIENT`. Данные начального каталога и клиентов являются вымышленными.

## Разграничение доступа

- Руководитель: полный обзор отдела, просмотр клиентов, броней, сделок и документов, создание и изменение свободных объектов, отчёты CSV, журнал операций. Не выполняет операции менеджера от его имени.
- Менеджер: просмотр каталога, добавление и изменение карточек клиентов, подтверждение или отклонение заявок, создание/отмена брони, проведение сделок, передача карточки договора, учёт результатов расчётов и регистрации. Не может подтверждать условия от имени клиента, редактировать каталог или получать отчёт руководителя.
- Клиент: каталог, подача заявки, отзыв ожидающей заявки, просмотр только своих бронирований, сделок и доступных документов, подтверждение условий договора.

Роль определяется сервером по учётной записи. Сессия хранится в базе, браузер получает HttpOnly-cookie. Пароли хранятся в виде PBKDF2-хешей с солью. Изменение пароля закрывает все текущие сессии этой учётной записи. Действия и данные ограничены на стороне API, а не только скрытием кнопок. При работе нескольких пользователей в разных окнах используйте отдельные профили браузера/приватные окна; кнопка «Обновить» получает свежие данные.

## Основной процесс

1. Клиент выбирает свободный объект, открывает карточку и подаёт заявку.
2. Менеджер открывает заявку, подтверждает её и создаёт сделку. При подтверждении объект становится забронированным. Одновременное подтверждение двух броней невозможно благодаря транзакции SQLite и уникальному индексу действующих броней.
3. Менеджер передаёт карточку договора, клиент подтверждает её условия в своём кабинете.
4. Менеджер отмечает запрос на подтверждение расчётов, затем фиксирует результат по полученному документу. Отказ приостанавливает сделку без освобождения объекта. Можно повторить запрос либо изменить способ оплаты и заново согласовать условия.
5. После подтверждения условий и расчётов менеджер завершает сделку: объект получает статус «Продано», бронь — «Завершено».
6. Руководитель видит рассчитанные по БД показатели и выгружает CSV. Отдельно менеджер может зарегистрировать полученные сведения о передаче на регистрацию и её завершении.

Результаты банковских расчётов и регистрации вносятся вручную; внешние API не подключены. Внутренняя карточка договора и подтверждение через учётную запись не заменяют юридически действительный договор или квалифицированную электронную подпись. Это локальная готовая сборка; для открытого интернет-развёртывания нужны HTTPS, защищённые cookie (`CRM_SECURE_COOKIE=1`), настройка инфраструктуры, ограничение частоты попыток входа, резервное копирование и дополнительный аудит безопасности.

## Проверка и структура

```bash
python -m pytest -q
```

Тесты используют отдельную временную БД: проверяют авторизацию, разграничение прав, создание и изменение записей, запрет двойной брони, отказ банка, повторное согласование, завершение сделки, сохранение БД и смену пароля. Скриншоты проверенных экранов находятся в `verification/`. Браузерная проверка выполнялась с настоящим API и SQLite через тестовый мост (не проверяет непосредственно передачу cookie самим браузером). API-тесты проверяют cookie и выход из системы.

В репозитории не следует хранить `venv`, `data/crm.db` или конфиденциальные данные. `.gitignore` уже настроен.
